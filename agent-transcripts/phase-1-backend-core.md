# Phase 1 — Backend core: FastAPI + PostgreSQL + sessions

## What was built

- `apps/api/app/config.py` — single `Settings` object (pydantic-settings), the one
  place `model_provider` and every other env-driven value is read.
- `apps/api/app/database.py`, `models.py` — sync SQLAlchemy 2.0 engine, `ChatSession`
  and `Message` ORM models. `Message` carries the audit columns the assignment asks
  to support later: `model_provider`, `model_name`, `retrieval_hit_count`,
  `citations` (JSONB), `latency_ms`, `error`.
- `apps/api/app/schemas.py` — Pydantic request/response contracts with real
  validation (`content` min/max length, etc).
- `apps/api/app/errors.py` — structured `{error, detail, code}` responses for 404,
  422 validation, 503 DB-unavailable, and a catch-all 500 that never leaks a raw
  traceback to the client (still logs the real exception server-side).
- `apps/api/app/logging_config.py` — structlog JSON logging, used by a request
  middleware in `main.py` and by the health/chat services.
- `apps/api/app/routers/system.py` — `/health` and `/config`, both do a *live*
  check (real `SELECT 1`, real `GET /api/tags` against Ollama) rather than a
  hardcoded 200.
- `apps/api/app/routers/sessions.py` — the four required endpoints.
- `apps/api/app/services/chat_service.py` — **intentionally a placeholder** for
  Phase 1. It persists the user message and a labeled placeholder assistant reply
  ("retrieval/agent not wired up yet") rather than fabricating a grounded answer
  before RAG exists. Replaced in Phase 3.
- Alembic wired up for real (`alembic/env.py` reads `DATABASE_URL` from the same
  `Settings` object the app uses, so migrations and the app can never drift out of
  sync on connection config). One real autogenerated migration,
  `e072768ca708_create_sessions_and_messages_tables.py`, reviewed by hand before
  applying (confirmed it only creates `sessions`/`messages` + the expected index,
  nothing spurious).
- `docker-compose.yml`, `apps/api/Dockerfile`, root `.env.example` — written now
  even though full compose verification is Phase 6/9, so the Postgres+pgvector
  service exists to develop against immediately.

## Dead end / correction: Postgres port collision

First `docker compose up -d db` run failed silently from the host side --
`alembic revision --autogenerate` errored with `password authentication failed for
user "lenny"` even though the credentials were correct. Root cause: this machine
already has an unrelated project's `pravaha-postgres-1` container bound to host port
5432 (confirmed via `netstat -ano | grep :5432` showing two listeners), so the new
container's publish either lost the race or Windows silently routed the connection
to the other instance. Fixed by moving this project's Postgres to host port 5442
(`POSTGRES_PORT=5442` in `.env`, `DATABASE_URL` for host-venv dev updated to match;
the in-Docker `DATABASE_URL` used by the `api` service is unaffected since it talks
to `db:5432` over the compose network, not the host port). Documented in
`docs/architecture.md` deployment section so a client engineer isn't surprised by a
non-default Postgres port if 5432 is taken on their machine too.

## Verification (real curl output, not paraphrased)

Ran against the actual stack (Postgres in Docker on 5442, API via uvicorn on the
host venv against it, Ollama already running locally on 11434):

```
GET /health         -> {"status":"ok","database":"ok","ollama":"ok","model_provider":"ollama"}
GET /config          -> {"model_provider":"ollama","anthropic_model":"claude-sonnet-5","ollama_model":"mymodel","anthropic_configured":false,"ollama_reachable":true}

POST /sessions {"user_id":"harsh"}
  -> 201 {"id":"5d4b9ae2-...","user_id":"harsh","title":null,"created_at":...}

POST /sessions/{id}/messages {"content":"What is product-market fit?"}
  -> 201 {"id":"b7a97bf0-...","role":"assistant","content":"Retrieval and the model
     agent are not wired up yet ... You said: 'What is product-market fit?'", ...}

GET /sessions/{id}/messages
  -> 200 [user turn, assistant turn] -- both present, correctly ordered by created_at

GET /sessions/00000000-0000-0000-0000-000000000000/messages -> 404
POST .../messages {"content":""} -> 422 {"error":"validation_error", ...}
```

**Restart test**: killed the uvicorn process (`taskkill /F /PID ...`), confirmed
`curl` connection-refused, restarted uvicorn fresh, re-ran `GET
/sessions/{id}/messages` -- both messages from before the restart came back
unchanged. This proves persistence is real (Postgres-backed), not in-process state.

**DB-down test**: `docker stop lenny-growth-assistant-db-1` while the API was still
running. `GET /health` correctly flipped to
`{"status":"degraded","database":"unreachable",...}` (still 200, since /health's
job is to *report* degradation, not fail); `POST /sessions` correctly returned
`503 {"error":"database_unavailable",...}` instead of crashing or leaking a
traceback. Restarted the DB container, confirmed `/health` recovered to `"ok"`
within one poll.

All of Phase 1's stated verification steps are satisfied for real, with the actual
request/response pairs shown above (not summarized/fabricated).
